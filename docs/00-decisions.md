## 背景：两类用户

整个项目的所有决策都绕着这个分类转，先明确：

| | A 类 | B 类 |
|---|------|------|
| 谁 | 作者本人这样的人 | 朋友、读者 |
| 特征 | 有 Obsidian、有自己的 AI Agent、愿意折腾 | 只想"对着微信说话，日记自动出现" |
| 要什么 | 数据契约稳定、可 hack | 装得上、用得起来 |
| 卡在哪 | 不卡 | `pip install` 报错就流失 |

**019 (Python 版) 是给 A 类的**，README 甚至是写给 A 类用户的 Agent 看的。
**020 (插件版) 是为了拿下 B 类。**

⚠️ 最大的未验证假设：**做出来到底有没有人连续用 30 天。**
作者自己都用不起来（见 D3）。所有工程投入的优先级都应该服从于"尽快验证留存"。

## D1 · 产品形态选 Obsidian 插件

**决策**：第一阶段做 Obsidian 插件，不做独立 exe/app。

**为什么不是别的形态**（这一步是物理约束，没得选）：

要做到「微信输入 → 用户自己电脑的本地 markdown」，链条上必须有个东西在**用户电脑上运行**。所以：

- ❌ **网页**：浏览器写不了任意本地文件（File System Access API 要每次授权、Safari 不支持、关页面就停）
- ❌ **小程序**：微信沙盒里，碰不到电脑
- ❌ **手机 App**：写不到电脑硬盘
- ❌ **纯云端**：违背"数据不上服务器"的底线

所以本地常驻程序是**必需的**，真正的问题只是：**它寄生在什么宿主里。**

**为什么是 Obsidian 而不是自己打包 exe**：

| | 自己打包 exe/app | Obsidian 插件 |
|---|---|---|
| 安装 | 下载→双击→过安全提示→配自启 | 市场里搜索→点安装 |
| 开机自启 | 要自己做 | Obsidian 开着就在跑 |
| 更新 | 要自己做 | 市场自动更新 |
| 签名 | mac 需 Apple 开发者账号 $99/年，Win 会报毒 | 无 |
| 跨平台 | Win/mac 各打一份 | Obsidian 已经解决 |
| vault 路径 | 要问用户 | 天生就在 vault 里 |

**插件形态把安装、自启、更新、签名、跨平台这五个最烧人的工程问题一次性外包给了 Obsidian。**

而且作者已经上架过 Obsidian 插件（`memo-lite`），分发流程趟过一遍。

**代价（必须认）**：
- 第一批用户**必须是 Obsidian 用户**。不用 Obsidian 的人，要先装一个 100MB 的软件才能用日记工具——对他们来说插件形态**反而更重**。
- Obsidian 不开着就收不到消息（但 cursor 机制应该能补拉，**待实测**）。

### 📌 2026-08-05 调研补充 —— 三条必须记进代价栏的确认结论

**① 技术上没有阻断性问题，审核大概率能过。【已确认】**
- 提交流程 2026-05 已改版：不再向 `obsidian-releases` 提 PR，改为在 `community.obsidian.md`
  开发者面板提交，**几分钟出结果**，通过后 24 小时内可搜到
- 政策对"连第三方服务器 + 传输用户内容"是 **allow-with-disclosure**：
  原文 "The following are only allowed if clearly indicated in your README"，
  含 "Network use. Clearly explain which remote services are used and why they're needed"
- Not allowed 黑名单（74 行）**无任何一条**针对第三方服务 / IM 集成 / LLM 调用
- 在架先例：`wechat-inbox-sync`（域名含 `channels.weixin.qq.com`）Review 为 Satisfactory；
  `telegram-sync`（270 issues + eval + 8 个外部域名）Review 为 Caution，**经人工审核通过**，
  48k 下载；**你自己的 `memo-lite` 440 issues 也照样在架**
- → **扫描结果是评分卡，不是准入闸门**

**② 🔴 Obsidian 关掉 = 插件完全停止，收不到任何消息。【已确认】**
源码级确认：`app.on("window-all-closed", () => { isMac || app.quit() })`。
Windows/Linux 关最后一个窗口即退出；macOS 不退但所有 BrowserWindow 已销毁 →
渲染进程没了 → 插件 JS 停止。

**这和当前 Python 版可独立常驻是本质差别，是我当初推荐插件形态时低估的一条。**
社区的 tray 类插件只是让窗口保持存在（从而落回后台节流），不是让插件脱离 Obsidian 跑；
且 `obsidian-tray` 依赖 Electron **已弃用**的 `remote` 模块，最后实质更新 2025-03。

**"开着"到底指什么 —— 精确定义**：

| 场景 | Python 版 (019) | 插件版 (020) |
|------|:---:|:---:|
| 电脑关机 | ❌ 停 | ❌ 停 |
| **电脑睡眠** | ❌ 停 | ❌ 停 |
| 电脑醒着，Obsidian 没开 | ✅ 跑 | ❌ 停 ← **唯一的差别** |
| 电脑醒着，Obsidian 最小化 | ✅ 跑 | ✅ 跑（有节流，但 HTTP I/O 在主进程，不受影响） |
| 电脑醒着，Obsidian 开着 | ✅ 跑 | ✅ 跑 |

- **睡眠不算开着**：整个系统冻结，所有进程停，网络连接断。
  这一点两个版本完全一样——019 的 README 自己也承认"电脑睡眠时提醒也发不出去"。
- **所以两种形态的真实差距只有一行**：电脑醒着但没开 Obsidian。
  对常年开着 Obsidian 的用户，这一行的杀伤力有限。
- ⚠️ **macOS 特有待测**：关窗口（Cmd+W）后 app 仍在 Dock，但源码显示
  BrowserWindow 已销毁 → 渲染进程没了 → **插件可能已经停了**。需要实测确认。

**🔴 由此推出一个更要紧的结论**：既然睡眠 = 停，那用户**每晚睡觉时电脑也睡觉，
每天都有 8+ 小时离线**。早上在床上用微信说的话，电脑还睡着，当场收不到。

**这不是插件版特有的问题，Python 版一模一样。**
→ **P0 实测①（cursor 能补拉多久）比原先以为的更关键**：
它不只关系到"要不要开 Obsidian"，而是关系到**每一天的常规使用**。
如果 cursor 只能补几分钟，那这个产品对"早上想记两句"的场景根本不成立。

**③ 移动端出局，`isDesktopOnly: true`。【已确认】**
移动端完全没有 Node.js / Electron API，`requestUrl` 走 Capacitor 原生实现，
桌面端结论不能外推；iOS/Android 会挂起后台应用（OS 级约束，Obsidian Sync 的
移动端后台同步 feature request 从 2021-10 开到现在仍未实现）。
同构先例 `obsidian-telegram-sync` 的 README 原文：
"would never be available on mobile platforms"。

**④ 用 Node `https` 而不是 `requestUrl`。【已确认】**
`requestUrl` 底层 Electron `net.request` **强制跟随系统代理，无法逐请求 opt-out**
（唯一后门 `session.defaultSession.setProxy()` 会影响整个 Obsidian）。
国内用户开着 Clash 时 iLink 请求会被强制走代理——而 019 花大力气做的正是反向的事。
合规没问题：用 Node API 只要求 `isDesktopOnly: true`，反正②③已经决定了这一点。

**为什么接受这个代价**：
在留存假设没被验证之前，花几周解决 mac 签名和开机自启，是在给一个还没证明有人要的东西铺路。而且 **Obsidian 用户是最可能持续记日记的人群**（本来就有记录习惯），从最容易转化的人群开始验证，成本最低、信号最准。

**什么时候推翻**：
插件版验证出留存后，再做独立 exe/app 覆盖非 Obsidian 人群。两种形态产出**完全一致的 markdown**，用户随时可以在两边迁移。

## D2 · 内建回顾能力（改变项目定位）

**决策**：020 内建"回顾/检索"，不再沿用 019 的"只做管道"定位。

**为什么**：
019 的 README 写着 *"回顾/检索/周报交给你自己的 Agent 在 vault 上做，本项目不做也不干涉"*。这句话是**写给 A 类用户的**——但：

> **B 类用户没有自己的 Agent。**

对他们来说这些功能等于不存在，产品就只剩一个录音笔：说话、存文件、没了。没有任何东西让他们明天再来。

**一石三鸟**：
1. 让它真的像个 Agent，而不是管道
2. 给 B 类用户明天再来的理由
3. **用户主动来问，就刷新了 context_token 的时间窗口**（见 `protocol-notes.md` 第 4 节）——回顾功能本身就是提醒问题的解药

**技术上很便宜**：日记就是本地 md，一个月也就几万字，直接读出来塞进 LLM 上下文。
**不需要向量库、不需要 RAG、不需要服务器。** 插件形态下读 vault 文件是原生能力。

**"Agent 感"具体是什么**（按价值排序）：
- 主动性：「昨天你说的那个面试，后来怎么样了？」← **这一句胜过前面所有功能**
- 「上周我都干了啥」→ 读本地 md → LLM 给一段回顾
- 「我最近是不是老在抱怨同一件事」→ 它真的看得出来

**代价**：需要 AI key 才能用（零 key 模式下回顾能力不可用，只能降级成简单的按日期列出）。
019 的"零 key 也完整可用"承诺，在 020 里要重新表述。

## D3 · 提醒做多路冗余，不指望微信推送

**决策**：不把「微信定时推送」当作留存的主力机制。

**为什么**：

**① 真正的死结（2026-08-05 调研确认，比原先以为的更糟）**：

```
用户每天写  → token 天然高频刷新 → 提醒发得出去（但他本来就不需要提醒）
用户连续没写 → token 陈旧        → 提醒发不出去（而这正是最需要提醒的时刻）
```

**提醒在最需要它的时刻必然失效。** 叠加"每天固定同一时钟、间隔接近 24 小时"，
越规律越发不出去。这就是"装了但用不起来"的技术根因。

**② 🔴 原来写的"20 小时限制"是编的。【已确认】**
腾讯官方源码、README、CHANGELOG、全部社区文档**没有一处提到 20 小时**，
"平台反骚扰规则"这个定性同样零出处。代码层面可确证它是本地拍脑袋的启发式：
`_is_token_fresh` 只做本地时间戳相减，**不发任何网络请求**，
而判定不 fresh 时**直接跳过、根本不调 sendmessage**——
这条链路从未、也不可能从服务端观测过真实窗口。
（社区流传的"24 小时"同样是假的，详见 `protocol-notes.md` 3.2。）

**真实窗口没有任何人知道。** 所以第一件事是**把预判删掉，改成"到点就发、按返回码记录"**——
现在是"我猜发不出去所以不发"，连试都不试，白白放弃了可能能发出去的时段。

**③ iLink 通道内确实没有换取推送额度的机制。【较可信】**
已知 9 个端点里没有模板消息、没有订阅授权、没有一次性推送凭证。
`sendmessage` 是唯一出口，而它依赖只能由用户入站产生的 `context_token`。
——但注意：**理由是"没开放这类接口"，不是"腾讯反对主动推送"**。
企业微信自建应用的推送侧就没有任何时间窗口（见下）。

**方案：三路冗余**

| 优先级 | 通道 | 可靠性 | 代价 |
|---|---|---|---|
| 主力 | **系统日历/提醒事项** —— 安装引导时让用户在手机上加一条每天 22:00 的重复提醒 | 100%，永不失效 | 土，要用户手动加一次 |
| 增强 | **iLink 推送** —— 删掉时间预判，到点就发、按返回码分流记录 | 尽力而为 | 真实成功率未知 |
| 辅助 | ~~Obsidian 本地通知~~ | ❌ **已否决** | 见下 |

⚠️ **"用 Obsidian 本地通知替代微信推送"这条被调研否决了**：Obsidian 的系统通知
只在 Obsidian 运行时触发，**且移动端根本不提供系统通知**（Reminder 类插件的长期已知限制，
社区解法是转投 ntfy 等外部服务）。对"随时随地用手机记日记"的用户，
这是把"窗口可能失效"换成了"手机上必然收不到"——**更差的一侧**。

**核心心智**：别指望单一通道解决留存。

**另一半答案在 D2**：回顾能力带来的"主动想来"，比任何推送都可靠。

### 🔑 2026-08-05 追加核实：提醒可能没那么难修

直接读腾讯官方源码后确认（详见 `protocol-notes.md` 3.4）：

- 官方的 contextToken store 是个**纯 `Map<string,string>`**——
  **没有时间戳、没有 TTL、没有过期逻辑**（grep `ttl|expire|stale|Date.now()` 命中数为 0）
- 它被**特意落盘**，注释写明是为了 "survive gateway restarts"——官方不但不丢旧 token，
  还专门保证跨重启存活
- 没有 token 时官方**只 warn 然后照发**，不拦截
- 官方 prompt 里明确指导怎么给微信用户**建 cron 定时任务**——
  定时主动推送是官方设计里的正常用例

**→ 019 的 `_is_token_fresh` 是官方实现里根本不存在的发明，
而它正是"连试都不试就跳过提醒"的那个开关。**

**第一优先级的修复因此变成：把这个预判整个删掉。** 有可能这一条就把提醒修好了。
在做任何多路冗余之前，先做这个。

### ❌ 企业微信旁路 —— 已放弃（2026-08-05）

调研发现**企业微信自建应用的推送侧没有任何时间窗口**【已确认，逐字核对
`developer.work.weixin.qq.com/document/path/90236`】：限制纯粹是流量阈值型
（每应用「账号上限数×200 人次/天」，对同一成员「30 次/分钟、1000 次/小时」），
**通篇无"用户须先互动"之类的条款**。这证伪了"微信一概反对主动推送"的直觉。

**但这条路已放弃，不做实测。** 决定于 2026-08-05，理由按强度排序：

1. 🔴 **即使技术上通，接入流程对 B 类用户完全不可能**：注册企业微信 →
   创建自建应用 → 配置企业可信 IP → 拿 corpid/secret → 成员关注微信插件。
   **这和 020 的存在理由（让不懂技术的普通人能用）直接矛盾。**
   而且"可信 IP"很可能要求固定 IP，家用动态 IP 直接出局——除非架中转服务器，
   那又违背"数据只在本机"。
2. **它只能解决"出站提醒"，收不了用户输入**（需要公网 HTTPS 回调）。
   最多是 iLink 的补充，不是替代，收益本来就有限。
3. 作者判断：企业微信与普通微信之间的接口只有"企业成员加微信用户为外部联系人聊天"，
   群机器人的消息不会落到普通微信里。
   （补充：企业微信历史上确有"微信插件"机制，Server酱这类推送服务用过它——
   但 2026 年是否还通没有核实，**且不影响上面第 1 条结论**。）
4. 这个调研方向的**核查 agent 本来就失败了**，全部内容标的是【未核查】，
   本来就不该当结论用。

**→ 提醒问题回到 iLink 通道内解决，见上面「追加核实」一节。**

## D4 · 日记只存一份，在用户指定的 vault 目录

**决策**：日记内容保存在用户在插件设置里指定的 vault 内目录，**只此一份**。
不做副本、不做云备份、不在插件目录里另存一份。

**为什么**：备份交给用户自己的同步盘（iCloud / OneDrive / 坚果云 / Obsidian Sync）。
多处保存 = 多处不一致 = 用户不知道哪份是真的。

**具体布局**：

```
用户的 vault/
├── .obsidian/plugins/wechat-diary/
│   ├── main.js / manifest.json / styles.css
│   └── data.json          ← 配置 + iLink token（见 D5 ⚠️）
└── 日记/                   ← 用户在设置里选，插件给个默认值
    └── 2026/
        └── 2026-08-05.md   ← 格式和 Python 版一字不差（见 D6）
```

**和 019 的差异**：019 用 `.env` 里的绝对路径 `DIARY_DIR`；020 用 **vault 内相对路径**。
因为插件天生活在 vault 里，而且只有走相对路径才能用 `app.vault` API
（能被 Obsidian 正确索引、触发链接更新、参与同步）。

数据契约里 `YYYY/YYYY-MM-DD.md` 的结构**一个字不改**，只是根从绝对路径变成 vault 相对路径。

## D5 · 运行时状态不落在 vault 可见区域

**决策**：iLink token、session 状态、用户 profile 一律走 Obsidian 官方的
`this.saveData()` / `loadData()`，写到 `.obsidian/plugins/wechat-diary/data.json`。

**为什么**：019 的 `data/*.json` 如果照搬到 vault 的普通文件夹，会被 Obsidian 索引、
出现在搜索结果里、被同步盘同步、甚至在图谱视图里冒出来。

**✅ 2026-08-05 调研给了官方答案：用 `SecretStorage`，不要用 `saveData` 存 token。**

- `saveData()` 写的是 `<configDir>/plugins/<id>/data.json`，**明文 JSON、在 vault 目录树内**。
  任何文件夹级同步（iCloud / Dropbox / Syncthing / Git）都原样带走，Git 场景极易误提交。
- **正确做法**：Obsidian 1.11.4+ 的官方 `SecretStorage` API
  （`app.secretStorage.getSecret / setSecret`），走 Electron `safeStorage`
  （macOS Keychain / Windows DPAPI / Linux libsecret）加密后存进 Electron localStorage，
  **不在 vault 里**，按 vault 隔离。
- 代价：需要 `minAppVersion ≥ 1.11.4`，老版本要有 data.json 降级路径。
  ⚠️ 一个坑：`isEncryptionAvailable()` 为 false 时 Obsidian **会明文落盘**，要处理这个分支。

**→ 决策：token 走 SecretStorage，其余非敏感配置（日记目录、提醒时间）留在 data.json。**

### 🔴 补记 2026-08-14 —— 这条决策制造了一个线上故障，v0.2.1 修

上面这个决策本身是对的，但它带来一个当时没想到的后果：**一份"绑定"被劈成了两半，
存在两个生命周期完全不同的地方**，而代码从头到尾假设两半同生共死。

| | 卸载插件 | 随 vault 同步 | 换设备/换路径 |
|---|---|---|---|
| `bot_token`（SecretStorage） | **不删** | **不走** | **丢** |
| `userId`/`botId`/`baseUrl`（data.json） | **删** | **走** | 跟着 vault |

任一半单独消失 → "半绑定"，而 v0.1.3 里没有任何一条路能走出来：
`bound = token && userId` 二值判定把它错判成"未绑定" → 解除绑定按钮被禁用 →
残留 token 又被塞进 `local_token_list` → 重新扫码必被服务端顶回 `binded_redirect` →
而那个分支的文案还是错的（见 `protocol-notes.md` 勘误）。**用户被锁死。**

**SecretStorage 的存储位置与隔离粒度（逆向 Obsidian asar 实测，1.13.x）**：
`safeStorage.encryptString()` → `app.saveLocalStorage("secrets-encrypted")` →
`localStorage["<appId>-secrets-encrypted"]`，落在 `%APPDATA%\obsidian\Local Storage\leveldb`。
**`appId` 是按 vault 的绝对路径登记的**（`obsidian.json` 的 `vaults` 映射），
且 `.obsidian/` 里没有任何携带 vault id 的文件。推论：

- 库路径变了（OneDrive 已知文件夹移动、换盘、改用户名、打开的是同步冲突副本）
  → 新 appId → **旧 secret 变孤儿**，而 data.json 跟着 vault 好端端地来了 = 半绑定。
- 换机器 → secret 为零，data.json 却随同步盘到了 = 半绑定。
- 卸载插件 → data.json 没了，secret 还在 = 半绑定（反过来的那一半）。

**修法（v0.2.1）**：
1. 绑定身份（userId/botId/baseUrl）**也存一份进 SecretStorage**（`wechat-diary-bind-identity`），
   与 token 同生命周期。data.json 丢了在 `onload` 里无感恢复。
2. 状态改三态 `bound / half / none`，半绑定不再伪装成未绑定，清理入口永远可用。
3. `binded_redirect` 按官方语义当成功；有 token 就启动管道，userId 为空时进
   "待认领"——**弹窗让人确认**才认主人（协议层没有 allowlist，不弹窗就是谁先说话谁当主人）。
4. 解除绑定拆成「只清主人身份（保留凭据）」和「彻底解除」。后者可能不可逆：
   服务端不补发凭据，清掉本机 token 后同一微信号重扫会被判 `binded_redirect`。
5. 从 secret 恢复身份时，`buf` 和 `recentSeqs` 必然是空的 → 服务端可能回吐积压，
   而写入用的是 `todayStr()`（报文里没有原始时间）→ 会把历史**按今天的日期重演一遍**，
   连「撤回」「结束」都会被重放。所以恢复后的第一波只推游标不落笔，等长轮询空一次再开始记。

**另外三条写文件的官方结论【已确认】**：
- API 顺位：`Editor` > `Vault.process` > `Vault.modify`，Adapter API 是最后手段
- ⚠️ **Obsidian 的"原子性"只是 in-process 串行队列**，底层 `fs.writeFile` 直接截断写，
  **没有 temp+rename** —— 崩溃/断电仍可能留半截文件。
  019 的 `写 .tmp + os.replace` 在 Obsidian API 里**没有对应物**，
  数据契约规则 2 要重新想怎么满足
- `Vault.create` 的 exists 检查和 write 不在同一事务内，有 TOCTOU 窗口
  → **按天建文件时应先 `getFileByPath`，拿到 TFile 就 append/process，拿不到才 create**
- 不要硬编码 `.obsidian`（用 `Vault.configDir`）；不要用 `vault.delete`（用 `trashFile`）

## D9 · 一天要有句号：告别语=收尾、夜间提示教在开头、「记：」逃生口（2026-08-19）

**起因**：谷雨实测一天记 8 段后发「好，结束」被当内容记进第 8 段，再发「结束」才封存。
感受是"只有'记下来啦 第 N 段'的复读，没有句号感"。9 条收尾语/告别语因为没人发光杆「结束」几乎从未出现过。

**决策**（三视角审稿后拍板）：
1. **识别层认人话**：前置应答词（好/好的/嗯/那/OK）剥掉后**只做词表精确匹配**、不走任何前缀兜底
   （「好早」「那完了」「好的撤销了订单」留在内容侧）；尾部剥 emoji/符号；复读折叠对全部命令生效。
2. **告别语=收尾，只收明确对 bot 说的**：晚安 / 我睡了 / 去睡了 / 睡觉去了 / 今天就到这(里/儿) / 今天先到这(里/儿) / 明天见。
   **光杆「睡了」「睡觉了」「先这样」「就这样」「到此为止」「写完了」不收**——记爸妈病历/宝宝作息的用户拿它们当状态记；
   标准同「在吗」：可能是内容就不收。告别语**回以同类**（"晚安 🌙 今天 N 段都收好了, 明天见"），不走「结束」的仪式池；
   空日子只道别，不接"想记什么直接发"。
3. **提醒不做推送、不按段数**：段数多的恰是最不需要收尾的备忘录用户；bot 只在你说话时说话。
   改为**当天第一条深夜（22 点起，`nudgeNightHour` 可改 data.json）消息**的回执附一句
   "(睡前跟我说声「晚安」, 我给今天收个尾 🌙)"——教在开头不在中途打断；一天一次、终身最多 3 次、
   用户手动收尾过一次就永久闭嘴；开页那条并进 tips，一条回执只挂一个括号。
4. **「记：xx」逃生口**：剥掉前缀强制原样落库，与「撤回」对称（一个救误记，一个救误吞）。
   有了它，任何词想当内容记都有路可走，词表争议的代价大幅降低。
5. **不加"明天记得来找我哦"**：像 App 留存话术；现有"明天见 / 明天我等你"够了。
6. **每条回执"记下来啦~ 第 N 段"不动**：N 是送达确认，随机化侵蚀信任。"不生硬"靠一天三个节点
   （开页 / 深夜那句提示 / 晚安）各说一次话，不是给每条回执化妆。

**顺手修的三个旧 bug**：finalizeDay 改三态（sealed/already/empty/error），跨天"已自动收尾"告知只给真自动封的
（此前用户昨晚手动「结束」了今早仍会被告知"自动收尾"）；封存后「撤回」保住封存行（撤光才连封存行一起清）；
`startsWith("撤回")` 兜底收紧为复读/指代尾巴（「撤回申请」「撤销订阅」回归照记）。

**落地后的第二轮审稿（26 个 agent 对抗复核）补的细则**：
- 「X啦」=「X了」等价（「我睡啦」「记完啦」）；前置应答词最多剥 3 层，形态补 好啊/好哦/好哈/好的呀/嗯呐、好+/行+（「好的好的晚安」「好好好结束」）；
  多段告别按词表贪心切词（「晚安 晚安」「晚安，明天见」「我睡了晚安」「好了，晚安，明天见」），任一段有词表外的字就是内容；
  头部 emoji 也剥（「🌙晚安」），书名号《》不剥（「《晚安》」是在记一首歌）；长度闸门按剥完噪音的正文算（「撤回！！！×14」仍是命令）。
- 第一人称睡觉变体补进告别词表：我先睡了 / 我该睡了 / 我睡觉了 / 我要睡觉了 / 我先去睡了 / 去睡觉了 / 晚安了 / 晚安明天见。
- **019 传下来的光杆「完了」移出 FINALIZE 词表**：它更常是感叹（「完了完了」「完了😭」），尾部剥 emoji/复读折叠上线后必被误吞——按本条"可能是内容就不收"的标准处理。想收尾说「结束」。
- 「撤回/撤销/删掉/删除」的指代尾巴白名单补齐（上面那条/那个/刚才/刚才发的…），复读间允许语气词（「撤回吧撤回吧」）；应答词剥壳后也走尾巴白名单（「好的撤回上一条」）。
- 空日子说了「晚安/结束」也计 finalize_count（说明会用了，提示永久闭嘴）；夜间提示的计数在**回执发送成功后**才落账（发不出去不烧额度）；跨天告知那条不挂夜间提示（顺延到下一条，一条回执一个括号）；
  「晚安」+图片同条先记图再收尾（数字一致）；只有 1 段时说"今天这一段收好了"；首次见面那条不再重复"说错了发「撤回」…"（欢迎语里已有）。
- 谷雨 8/19 实机第一轮反馈补的：「继续记录/继续/接着记」等宣告与「开始记日记」同类——回"直接发就行~（「结束」只是收尾标记, 之后发的照样记）"，不落库；长句「明天继续记录血压」照记（精确匹配不做包含）。
- 顺手修的取名层旧 bug：STRIP_CHARS / CLAUSE_SPLIT_RE 里全角标点原来丢了（「叫我小明！」会把感叹号存进名字）。
- **记录在案、未改（产品裁决）**：取名轮第二条 ≤10 字的短句（「今天好累」「买菜」）会被裸兜底当成名字吞掉，违反"取名永不吞内容"——需谷雨定：裸兜底命中时是否同时把原句落库，或收紧兜底长度。

**状态字段**：`profile.finalize_count` / `profile.nudge_count`（跟人走），`session.nudged_date`（逻辑日），`settings.nudgeNightHour`（默认 22，无 UI）。
契约文件格式不变（封存标记同一格式，触发方式不影响格式）。测试 311 断言。

## D10 · 提醒复活 + 管道补全：文件/视频/语音兜底（2026-08-19）

**背景**：公众号用户想"转发文件/聊天记录给 bot"（§见 protocol-notes §8：转发是腾讯的墙，但对话框里直发文件/视频协议全支持，020 一直静默扔掉）；谷雨定优先级：**提醒 > 语音兜底 > 文件（含视频）**，并澄清定位：**这是笔记不是网盘，文字为主图片为辅**——但"发出去=记下了"对所有类型成立，静默扔掉肯定不行。

**提醒（谷雨拍板）**：默认**开**；默认 21:30（可改，设置页有 UI）；**今天（逻辑日）什么都没记才提醒**，记过就不打扰；一天最多一次；文案多版本**轮流**（不是随机）；**连续 3 天没写就闭嘴**，用户一回来（写任何东西）计数清零、提醒恢复。

**实现原则（019 的教训，D3）**：
- 019 的 `_is_token_fresh`"20 小时窗口"是编的，判定不新鲜连试都不试——**020 到点就发、零预判、按返回码记录**（`session.reminder_last_result`），真实送达窗口发着发着就知道了。
- 插件只在 Obsidian 开着时活着：到点没开，之后打开**补发**（同一逻辑日内、还没记、没提醒过）。
- 防误提醒：发送前提是**最近一轮长轮询已完成**（`_pollSettledTs` 3 分钟内）——电脑刚唤醒时今天的消息可能还没补收，countDay=0 是假象。
- 防双发：先记账（`reminded_date`）再发送，失败当天不重试。
- README 诚实写明"只在电脑开着 Obsidian 时发得出"。

**语音兜底**：转写失败（`voice_item.text` 空）从"请重说"（=内容丢了）改为**下载原始音频存 attachments**（🎤 前缀块），回执讲清"没转出文字、原音频已存、可重说"。格式按 magic bytes 嗅探（SILK/mp3/ogg/wav/amr），认不出按 encode_type 兜底。SILK 在 Obsidian 里放不了，但"什么都别丢"优先，转码工具在 vault 侧。

**文件/视频接收**：类型 4/5 落 attachments，保留原文件名（消毒后加日期时间前缀），当天笔记插 wikilink 块。
- **md5 双重用途**：①解密校验——解出来对不上就拒收（别把密文写进库）；②**重复文件复用**——微信 CDN 对重复内容复用旧密文却发新随机 key，重发同一文件必解密失败（官方仓 #193），020 靠"md5 见过→直接引用本地那份"绕过（`ilink.fileMd5s`，上限 200 条）。
- 超 100MB（协议上限）不下载直接告知；解密可疑时回执教用户"改个名再发"。
- 「晚安」+媒体同条：媒体先落库再收尾（与图片同规则）。

**数据面**：settings +`reminderEnabled`/`reminderTime`；session +`reminded_date`/`reminder_streak`/`reminder_idx`/`reminder_last_result`；ilink +`fileMd5s`。契约新增：附件块 = wikilink 块（文件/视频/语音兜底同图片），语音兜底块带 `🎤 ` 前缀（v1.2 追加说明，格式无破坏）。

**落地后审稿轮（16 agent 对抗复核，13 条全坐实全修）**：设置页时间校验与 reminderDue 统一（`REMINDER_TIME_RE`，越界回退+Notice，半截输入不落盘）；重扫码换管道时 `_pollSettledTs` 归零（防拿旧管道的新鲜度误发）；提醒在途时的新写入不被 streak++ 覆盖（`_writeGen` 写入代数）；开关关着不再每分钟读文件（countToday=0 预判）；说过「晚安/结束」的空日子当天提醒也压掉；视频版失败文案分型（🎬，不教"改名再发"）；磁盘满说"存附件失败"不说图片；`attachmentPathNamed` 超长扩展名/全毒字符名/字节上限三处补洞（防 ENAMETOOLONG 误报为网络问题）；取名轮「晚安」+文件同条也先写后封。**记录在案未修（接受）**：countDay 读文件异常时按 0 算，极端情况下可能多发一条提醒（无害）。测试 384 断言。

仍是标准 markdown + WAV 文件——手机端/卸载插件后是 Obsidian 原生播放器，照样能听；文字照旧可搜索；「撤回」整块一起撤（音频文件保留，同图片规则）。

**解码**：微信语音是 SILK v3，Obsidian 播不了。内嵌 silk-wasm@3.7.1（MIT © idranme，官方微信插件同款；讽刺的是官方把它放 devDependency 标准安装装不上，线上实际没在转码——我们内嵌后比官方完整）。wasm 以 base64 内嵌（main.js 190KB→541KB），两处 `silk_default()` 打 wasmBinary 注入补丁短路文件/网络加载（Obsidian 渲染进程兼容，纯 Node 环境双验证）。输出 24kHz/16bit/mono WAV（官方口径），约 2.9MB/分钟。微信 SILK 带 0x02 前缀，规范化成恰好一个（无前缀补、双前缀不会发生）；非 SILK（mp3/ogg）不硬解，走 D10 原始字节兜底。

**行为规则**：
- 转写文字**照走意图识别**——语音说「结束」还是封存命令，不会被存成音频块；只有"记录"意图的语音才存原声。
- 任何失败（下载/解码/写盘）**静默降级纯文字**——文字是本体，音频是增强，回执照常，不打扰用户。
- D10 的转写失败兜底同步升级：先试解码成可播的 WAV，解不开才存原始字节。
- 回执文案不变（"🎤 记下来啦~ 今天第 N 段"），开关是显式选择，不用每条重复确认。

**气泡渲染**（仅桌面端装了插件时；样式层，不碰数据）：
- 识别 `…-语音.wav` 的 embed（只动本插件写的附件，用户自己的 wav 不碰），替换成微信样式气泡：绿底、喇叭三弧线图标、时长"4″"、宽度随时长小幅增长；点击播放/暂停，播放中三弧线循环点亮动画；同时只放一条（微信行为）。
- 阅读视图走 registerMarkdownPostProcessor；Live Preview 的 embed 不走它，用 MutationObserver 兜底（dataset 标记防重复处理）。亮暗主题各配色。
- 手机端无插件（isDesktopOnly）→ 原生播放器，能听没气泡，README 写明。

**成本与账**：main.js +350KB（一次性）；每分钟语音约 2.9MB 计入 vault、被同步盘带走——所以默认关。MIT 声明已在内嵌段落注明。

**落地后审稿轮（18 agent，15 条全坐实全修/记录）**：气泡渲染五处重做——命名正则收紧到本插件完整格式（「英语语音作业.wav」不再误伤）、阅读视图"气泡+原生播放器并存"（实测确定性时序而非竞态）改为 append+CSS 隐藏原生、共享单个播放器（LP 重建 widget 不再攒 Audio/孤儿续播，时长改从文件大小算）、metadataCache 未就绪不打标（留给下轮重试）、键盘/读屏可达（role/tabindex/keydown/aria 状态/focus 环/reduced-motion）；observer rAF 攒批；「叫我XX」称呼收紧 ≤4 字（「叫我妈过来吃饭」照记——存量洞，D11 后成了唯一取名入口才修）；文字+语音混合条也存原声；垃圾 SILK 解出 <0.2s 噪声按失败算（兜底保原始字节）；wasm 坏时的 unhandledRejection 已消（ba.catch）；首条非记录文字+媒体同条的 tips 重复已剥；设置 desc 消歧（气泡不随开关关闭）；死常量清理。**记录在案未修（接受）**：升级瞬间恰好停在旧版取名轮的用户，其回答「跳过/名字」会被当内容落库（一次性窗口，内容多记不丢）；弹出窗口(popout window)里 LP 模式暂无气泡（原生播放器兜底）。测试 405 断言。
