# 数据契约 v1 (data contract)

> ⚠️ **本文件是副本，权威版本在 `019Dairy/docs/data-contract.md`。**
>
> 任何修改必须**两边同时改**，否则 Python 版和插件版产出的日记会不兼容，
> 用户在两种形态之间迁移时格式就断层了。见 `00-decisions.md` D6。
>
> 上次与权威版同步：2026-08-05（对应 019 提交 `8febfd1`）

wechat-diary 只做一件事: 把微信消息写进你的 vault。本文件定义写入格式——
这是本项目与"任何管理这个库的 Agent"之间的接口, 破坏性变更会升版本号。

## 目录结构

```
<日记根目录>/
├── 2026/
│   ├── 2026-07-15.md      # 每天一个文件, 文件名 = 北京时间日期
│   └── ...
├── attachments/           # v1.1 起; 目前只有插件版(020)产出, 见规则 7
│   └── 2026/
│       └── 2026-07-15-2104-a3f1.jpg
├── 剪藏/                  # 插件版网页剪藏扩展, 见规则 8
│   ├── 2026/
│   │   └── 2026-08-29-文章标题-a1b2c3d4e5.md
│   └── assets/
│       └── 2026/
│           └── 2026-08-29-a1b2c3d4e5/
│               └── 01-图片内容哈希.png
└── _backup_v1/            # 仅 v1→v2 迁移时产生, 确认无误后可手动删除
```

**"日记根目录"在两种形态下的含义不同**（这是唯一的实现差异，结构本身一字不改）:

| 形态 | 日记根目录 |
|------|-----------|
| Python 版 (019) | `.env` 里的绝对路径 `DIARY_DIR` |
| 插件版 (020) | **vault 内的相对路径**，用户在插件设置里选（默认 `日记/`） |

插件版必须走相对路径 + `app.vault` API，才能被 Obsidian 正确索引、
触发链接更新、参与同步。见 `00-decisions.md` D4。

## 文件结构

```markdown
---
date: 2026-07-15
weekday: 周三
source: wechat-diary
---

# 2026-07-15

**21:04**

正文段落。同一分钟内的多条消息共享一个时间戳段头。

🎤 语音消息以 🎤 前缀标记 (文本为微信自动转写, 未配 AI key 时为转写原文)。

**21:10**

另一个时间点的段落。

---
_(今日封存于 23:02)_
```

## 规则 (对 Agent 的承诺)

1. **只追加**: 程序永不修改/删除历史段落 (用户主动「撤回」只删最后一条消息)
2. **原子写入**: 先写 .tmp 再 replace, 文件不会出现半截内容
3. **时间戳**: 所有日期/时间为北京时间 (Asia/Shanghai, 可经 TIMEZONE 配置)
4. **frontmatter**: 仅在文件创建时写入, 之后不再更新; 字段只增不改
5. **封存标记**: `_(今日封存于 HH:MM)_` 表示当天已收尾, 可能不存在。触发方式不影响格式:
   用户说「结束」或告别语(「晚安」「今天就到这」等, 020 v0.3.1 起), 或跨逻辑日时自动写入
6. **消息计数**: 一个 `\n\n` 分隔块为一条消息; 排除 `# ` / `**HH:MM**` /
   `---` / `_(` 开头的块
7. **附件 (v1.1 图片; 2026-08-19 起扩展到文件/视频/语音原音频, 020-only)**: 附件单独成块,
   内容是一个 vault 全路径 wikilink; 文件/视频保留原文件名(消毒后加日期时间前缀);
   语音音频块带 `🎤 ` 前缀(区别于图片/文件)。开启「保存语音原声」后(2026-08-20 起),
   语音块 = `🎤 ![[..wav]]` + 单个换行 + 转写文字——**仍是一个块 = 一条消息**,
   读取方把整块当一条语音记录, 首行是音频、其余行是文字。图片规则不变:
   `![[<日记根目录>/attachments/YYYY/YYYY-MM-DD-HHmm-xxxx.ext]]`。
   它按规则 6 计为一条消息, 「撤回」照常撤得掉。
   附件文件本身**永不删除**——撤回只删笔记里的引用, 留下孤儿附件由用户处置
   (规则 1「只追加」的延伸: 程序不删用户的原始素材)。
8. **公众号链接剪藏 (020-only)**: 默认只对 `mp.weixin.qq.com` 链接提取正文；其它网站必须由
   用户主动打开设置开关。剪藏文件写入 `<日记根目录>/剪藏/YYYY/`，图片写入其
   `assets/YYYY/YYYY-MM-DD-文章身份哈希/` 子目录；用户可把剪藏目录改成其它 Vault 相对路径。
   剪藏 frontmatter 至少包含 `source_url`、`canonical_url`、`identity_url`、`source_site`、
   `author`、`published`、`clipped_at`、`source`、`web_clip_image_total`、
   `web_clip_image_count`、`web_clip_image_failed` 和 `tags`。当天日记中的同一个消息块先保留
   用户发送的完整原句，下一行写 `[[剪藏文件路径|🔖 标题]]`；这是一个块、计作一条消息。
   「撤回」删除这个日记块，但**永不删除**剪藏文件和已下载图片。

## 给管理此库的 Agent 的建议 (非约束)

- 回顾/检索/周报等在 vault 上直接做, 不要反向修改本程序的写入格式
- 需要给日记补充元数据时, 建议新增 frontmatter 字段而非改动已有字段

## 附: 插件版 (020) 的实现备注

以下不属于契约本身，只是记录插件形态下如何满足上面的规则。

- **规则 2「原子写入」**: Python 版靠 `写 .tmp → os.replace()`。插件版要用
  Obsidian 的 `vault.modify()` / `adapter.write()`，**这些 API 是否原子未确认**
  （调研中）。如果不原子，需要自己实现等价保护——否则崩溃时可能写出半截文件。
- **规则 3「时间戳用北京时间」**: 019 有 `config.now_bj()` 强制走时区，
  禁用裸 `datetime.now()`。TS 版同样要有一个统一入口，禁止直接 `new Date()`
  取日期——**文件名就是日期，这个不能错。**
- **规则 1「只追加」**: 插件版更要小心——Obsidian 里用户可能正好在编辑今天的
  日记文件。写入前要考虑和编辑器缓冲区的冲突（`vault.process()` 可能比
  `read` + `modify` 安全）。**待验证。**
- **规则 6「消息计数」**: 计数逻辑照搬 019 的 `count_messages`，注意排除
  `# ` / `**HH:MM**` / `---` / `_(` 开头的块。

## 契约 v1.1 — 图片附件 (2026-08-12)

**⚠️ 这是本副本先行、权威版(019)尚未同步的一条变更。** 按 D6, 019 侧必须跟着改文档,
否则契约两边不一致。具体状态:

- 019 (Python 版) **不产出**图片块 —— 它连 IMAGE item 都不解析, 行为不变, 老日记不受影响。
- 019 也**不需要能写**图片: 契约对它的要求只是「读到 `![[...]]` 块时当作一条普通消息,
  别当成坏数据去修」。它的 `count_messages` 本来就只按块首字符排除, 天然满足。
- 因此这是**向后兼容的增量**: 020 写的库 019 能继续追加, 反之亦然。
- 附件目录名 `attachments/` 与 Obsidian 默认附件目录同名但**不复用**用户的全局附件设置:
  日记的图必须跟日记一起备份/迁移, 挂在别处会在换库时断链。

## 契约 v1.2 — 逻辑日: 凌晨 4 点前算前一天 (2026-08-16)

**"文件名 = 日期"里的"日期"自 v1.2 起指【逻辑日】**: 一天的边界不是零点,
而是凌晨 `dayStartHour` 点(默认 4, 020 在 data.json 可配, 无 UI)。
02:30 记的东西落在**前一天**的文件里, 段头时间戳仍写真实时间(`**02:30**`)。

- 动机: 备忘录/日记用户的"一天"到睡觉才结束, 夜猫子睡前的记录属于"今晚"。
  固定边界取代了 020 v0.3.0 前的滚动宽限期(30 分钟内续写算前一晚)——
  规则一句话讲得清, 且"凌晨 1 点新开一段"也不再落错天。
- frontmatter 的 `date`/`weekday` 与文件名同步, 都按逻辑日。
- 读取方(含 019 的 count_messages)无需任何改动: 文件内部结构一字未变。
- 019 (Python 版) 已于 2026-08-16 同步实现 (`DAY_START_HOUR` 环境变量, 默认 4),
  两实现同一深夜写进同一文件。
- 附带行为说明(0.3.0 单模式): 封存标记之后仍可能出现追加段——用户「结束」后
  又发消息时照记不误(规则 1"只追加"优先于封存行位置)。读取方不应假设
  封存行必在文件末尾。

## 契约 v1.4 — 路径可配置 + 共用文件模式 (2026-08-30)

**⚠️ 这是本副本先行、权威版(019)尚未同步的一条变更。** 按 D6, 019 侧必须跟着改文档,
否则契约两边不一致。019 的代码不用改(理由见下), 但文档要写明它不支持哪些部分。

### 路径布局自 v1.4 起是默认值

- v1 的目录结构(`<根目录>/YYYY/YYYY-MM-DD.md` + `<根目录>/attachments/YYYY/`)
  自 v1.4 起是**默认值**, 不再是唯一形态。默认值下产出与 v1.2 逐字节相同。
- 020 用户可在设置里改两项:
  - 日记文件路径格式 `settings.pathFormat`: moment 格式, 相对根目录, 不含 `.md`,
    默认 `YYYY/YYYY-MM-DD`。字母是日期代码, 固定文件夹名要放方括号(`[daily]/YYYY/MM/YYYY-MM-DD`)。
  - 附件位置 `settings.attachmentMode`: `diary`(默认, 根目录下 `attachments/YYYY/`) /
    `obsidian`(跟随 Obsidian 的附件设置) / `custom`(`settings.attachmentFolder` 为库里的文件夹路径, `/` = 库根目录; 可选 `settings.attachmentSubFormat` 为 moment 格式的子路径, 如 `YYYY/MM`; 相对库根目录, 不受 diaryFolder 影响)。
  - 根目录 `settings.diaryFolder` 允许填 `/`, 表示库根目录。
- **读取方怎么找文件**, 二选一:
  1. 读 020 的 `data.json`: 用 `settings.diaryFolder` + `settings.pathFormat` 渲染出路径。
  2. 不看设置, 按 frontmatter `source: wechat-diary` + `date` 在全库识别。
     注意: 共用文件模式下的文件**没有**这个 frontmatter(见下节), 这条路只能找到独立文件。
- 附件的 wikilink 仍是 vault 全路径。读取方不需要知道附件位置设置。
- 独立模式下若文件不是插件建的(frontmatter 没有 `source: wechat-diary`), 020 仍追加, 但消息计数只数第一个 `**HH:MM**` 段头之后的块, 段头之后没有块时不写封存行、「撤回」拒绝。019 无此规则。
- **019 只支持默认布局。路径可配是 020-only。** 把 019 指向一个改过路径格式的库,
  它会按默认布局另建文件, 两边不会写进同一个文件。

### 共用文件模式 (`settings.sharedDailyNote` = true, 默认 false)

- 插件不独占文件。它独占**已有文件里的一节**。文件本身是用户的每日笔记, 头部、其他节都归用户。
- 节标题行 = `## <标题>`。标题文字以 `settings.sectionHeading` 为准, 默认「微信随手记」, 级别固定二级。
  读取方先读这个配置; 拿不到配置时按 `## <标题>` 全库搜索。
- 节的范围: 从标题行起, 到**下一个任意级别的标题行**(`^#{1,6} `)或文件末尾。
  - 代码围栏里的 `#` 行不算标题, 既不开始一节, 也不结束一节。围栏行 = 行首至多 3 个空格后接 ``` 或 ~~~ 的行, 每遇一行翻转一次围栏状态。
  - 文件开头 frontmatter 里的 `#` 不算。frontmatter 没有闭合行时不当 frontmatter 处理, 从头扫。
  - 同名标题出现多次时, 第一个算数。
- 节内格式与独立文件完全一致: 段头 `**HH:MM**`、`\n\n` 分隔的块、封存行。规则 1–7 在节内同样成立。
- 节内**没有 frontmatter, 没有 `# 日期` 标题**。日期取所在文件的每日笔记日期(文件名按 `pathFormat` 渲染)。
- **节标题一旦存在, 插件不删。** 「撤回」撤到空时只清正文, 标题行留着。标题可能是用户写在模板里的。
- 节内用户手写的内容, 插件当成自己的: 计入消息数, 可能被「撤回」删掉。
- 写入只改节的范围。节之后的内容逐字节不动; 标题前允许多出一个空行。
- 文件可能含 CRLF(用户的工具产出)。插件写回节内用 LF, 节外字节不碰。读取方按 LF 处理节内即可。
- 撤回、封存、计数遇到文件不存在或没有节时不建文件、不建节。只有写入新内容会建。

### 转义

- **共用模式**: 写入方对节内任何以 `#`×1–6 + 空格开头的行, 以及以(至多 3 个空格后)``` 或 ~~~ 开头的行, 行首加 `\`。
  目的是插件写的内容永远不会变成标题行, 节的边界才守得住。`#tag`(`#` 后无空格)不受影响。
- **独立模式**: 规则不变, 仍只对首行 `# ` 转义。
- **读取方**: 行首 `\#` 视为原文 `#`, 行首 `\```/`\~~~` 视为原文围栏符。旧文件与 019 的产出不保证此规则
  (019 与 0.4.0 之前的 020 只转义首行 `# `; 第二行起的 `## x` 原样存)。
